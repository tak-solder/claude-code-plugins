# 施策リファレンス

`/private-actions-cost-reduction` で使う、施策ごとの効果・リスク・判断基準。

## 料金の前提

料金は変更されることがある。費用を計算する前に、可能であれば公式ドキュメント（GitHub Actions の runner pricing）で最新の単価を確認する。確認できない場合は下表の値を使い、報告にその旨を書く。

| ランナー | vCPU / メモリ（プライベート） | 単価（目安） | 特徴 |
|---|---|---|---|
| `ubuntu-latest` / `ubuntu-24.04` など（x64） | 2 / 8GB | $0.006/分 | 標準。Docker あり |
| `ubuntu-24.04-arm` / `ubuntu-22.04-arm`（arm64） | 2 / 8GB | $0.005/分 | x64 と同じスペック |
| `ubuntu-slim`（x64） | 1 / 5GB | $0.002/分 | コンテナ上で動く。Docker なし、ジョブは 15 分まで、ツールは最小限 |

- 課金はジョブごとに 1 分単位で切り上げる。
- 無料枠はドル建てで、単価の安いランナーを使うと無料枠の消費も減る。
- パブリックリポジトリの標準ランナーは無料（パブリックリポジトリの `ubuntu-latest` は 4 vCPU / 16GB）。

## Tier 1（必ず対応する）

### 1-1. 実行条件の見直し（対象ブランチ・paths）

- **内容**：重いワークフローが、関係のないブランチやファイルの変更でも動いていないかを確認し、`branches` / `paths` を絞る。
- **確認すること**
  - `pull_request` の `branches`：デフォルトブランチ向けの PR だけで十分な検証（本番イメージのビルドなど）が、作業ブランチ向けの PR でも動いていないか。
  - `push` の `branches`：すべてのブランチへの push で動いていないか（PR と二重に動いていないか）。
  - `paths`：ドキュメントだけの変更などで動いていないか。
- **リスク**
  - `paths` の書き漏れで、必要な CI が走らない。依存関係のファイル（lockfile、ビルド設定、ワークフロー自身）を必ず含める。
  - `paths` で止まったワークフローのジョブを branch protection の required checks にしていると、「待機中」のままでマージできなくなる。
    `gh api repos/{owner}/{repo}/branches/{default}/protection` で required checks を確認し、該当する場合は `paths` を使わずにユーザーに相談する。
  - 作業ブランチ上の不具合に気づくのが遅れる。

### 1-2. キャッシュ

- **内容**：毎回同じ処理を繰り返している箇所にキャッシュを入れる。
  - 依存：`actions/setup-*` の `cache` 入力（npm / pnpm / yarn / pip / composer / gradle など）、または `actions/cache`
  - Docker のビルド：`docker/setup-buildx-action` + `docker/build-push-action`（または `docker/bake-action`）の `cache-from` / `cache-to` に `type=gha`
  - 静的解析・型チェックの結果キャッシュ（ツールが対応している場合）
- **リスク**
  - キャッシュが空の初回は、保存する分かえって遅い。効果は 2 回目以降で測る。
  - GHA キャッシュはリポジトリあたり 10GB まで。大きなイメージは他のキャッシュを押し出す。
  - キャッシュキーに依存・設定のハッシュを含めないと、古い結果を使ってしまう。

## Tier 2（ユーザーが選択したものを、検証してから適用する）

### 2-1. ARM ランナー（`ubuntu-24.04-arm`）

- **効果**：単価が約 17% 安い。実行時間が同程度なら、その分そのまま削減。
- **適用できる条件**
  - 依存（ネイティブバイナリ、コンテナイメージ、OS パッケージ、セットアップ用 action）が arm64 に対応している。
    - コンテナイメージは、digest 固定の場合でもマルチアーキテクチャの index を指しているか確認する。
  - デプロイ先と同じ CPU アーキテクチャでのビルドを必要としない（x64 向けのコンテナイメージや Lambda などのビルドは対象外）。
- **リスク**：本番が x64 の場合、片方のアーキテクチャだけで起きる不具合を見逃す可能性がある。依存を追加するたびに arm64 対応の確認が必要。

### 2-2. Vitest の `isolate: false`

- **対象**：Vitest を使っていて、テスト本体より準備（setup / environment）の時間が長いプロジェクト。Vitest の出力の `setup` / `environment` の時間で判断する。
- **効果**：テストファイルごとの実行環境（jsdom、Workers ランタイムなど）の作り直しをやめ、準備の時間を減らす。
- **必要な対応**（`isolate: false` だけでは失敗することが多い）
  - `restoreMocks: true` / `unstubGlobals: true` を有効にする。
  - setup ファイルで、ファイルごとの初期化を自前で行う（`vi.resetModules()`、testing-library の `cleanup` の明示登録、Web Storage の初期化、DB のリセットなど）。
  - ファイルの実行順をシャッフルしても通ることを確認する（`--sequence.shuffle` と `--sequence.seed`）。
  - 規約（spy / stubGlobal / fake timers はファイル内で必ず後始末する）をプロジェクトのドキュメントに追記する。
- **リスク**：モジュールの状態やモックがファイルをまたいで残り、テスト同士が影響し合う。原因の分かりにくい失敗が起きる。

### 2-3. テストの並列化

- **対象**：テストを直列で実行しているが、テストランナーが並列実行に対応している（Vitest / Jest の workers、Pest / PHPUnit の parallel、pytest-xdist など）。
- **効果**：テスト時間が短くなる。テストが DB やネットワークの待ち時間を含む場合、**コア数を超える並列数でも速くなることがある**（待っている間に別のワーカーが CPU を使えるため）。並列数は 2 / コア数 / コア数の 2 倍などを比べて決める。
- **必要な対応**：DB・キャッシュ・一時ファイルをワーカーごとに分ける。実行順に依存するテストを直す。
- **リスク**：並列数を増やすほどメモリ不足のおそれがある。実行順に依存するテストが表に出てくる。

### 2-4. Draft PR のスキップ

- **内容**：`pull_request` の `types` に `ready_for_review`（必要なら `converted_to_draft`）を加え、ジョブに `if: github.event.pull_request.draft == false` を付ける。push イベントでも動くワークフローでは `if: github.event_name != 'pull_request' || github.event.pull_request.draft == false` とする。
- **効果**：Draft で作業してから Ready にする運用なら、実行回数が減る。
- **リスク**：Draft 中は CI の結果が分からない。依存の自動更新 Bot など Draft を使わない運用では効果がない。
- **検証**：実行時間ではなく、Draft 状態で push したときにジョブがスキップされること、Ready にしたときに実行されることを確認する。

## Tier 3（トレードオフを理解したうえで、選択された場合のみ）

### 3-1. CI 本体を `ubuntu-slim` に

- **効果**：単価 1/3。実行時間が 3 倍未満なら得。
- **向いているジョブ**
  - lint・型チェック・ユニットテストを順番に実行する CI（x64 で数分以内）。もともと CPU を使い切っておらず、1 vCPU でも遅れが 2 倍前後にとどまる。
  - DB ファイルを使うテスト（DB ファイルを tmpfs に置けば遅さを回避できる。例：`TMPDIR=/dev/shm`）。
- **向いていないジョブ**
  - 複数プロセスで CPU を使い切る結合テスト（1 vCPU になり数倍遅くなる）。
  - Docker・`services:`・`container:` を使うジョブ（Docker がない）。
  - 大きなメモリを確保するツールを使うジョブ（メモリ 5GB）。
  - 15 分を超えるジョブ（強制終了され、延ばせない）。
- **よくある失敗と対処**
  - メモリ不足で落ちる：ツールのメモリ使用量を抑える設定を探す（例：大きなバッファの確保を無効にする環境変数）。
  - ディスク I/O が遅い：一時ファイルや DB ファイルを `/dev/shm` に置く。
  - タイムアウト：テストランナーのテストごとのタイムアウトが既定値を超える場合は延ばす。
  - ランタイムのセットアップが遅い：ランタイムが事前に入っていないため、毎回 30〜60 秒の準備が加わる。
- **リスク**：待ち時間が延びる。回避策の設定が増え、ワークフローが複雑になる。

### 3-2. デフォルトブランチへの push もキャンセル対象にする

- **内容**：Tier 0 の `concurrency` では、PR 以外の実行を `github.run_id` で別グループにしてすべて検証している。これを PR と同じく `${{ github.workflow }}-${{ github.ref }}` のグループにまとめ、`cancel-in-progress: true` にする。デプロイ系には適用しない。
- **効果**：マージが続いたときの実行回数が減る。
- **リスク**：途中のコミットが未検証のまま残る。
- **検証**：実行時間の比較は不要。設定の妥当性（デプロイ系が対象外であること）を確認する。

## ランナーの選び方

```
デプロイ先と同じアーキテクチャ、または Docker が必要？ ── Yes → x64
        │ No
数分以内に終わる軽いジョブ？ ── Yes → ubuntu-slim（Tier 0）
        │ No
CPU を並列で使い切らず、メモリ 5GB・15 分以内に収まる？ ── Yes → ubuntu-slim（Tier 3）
        │ No
依存が arm64 にそろっている？ ── Yes → ARM（Tier 2）
        │ No
        └→ x64
```
