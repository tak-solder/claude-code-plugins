# GitHub Actions の実行コスト削減

現在のリポジトリの GitHub Actions ワークフローを見直し、実行コストを下げる。

- 施策の詳細（効果・リスク・判断基準・料金）は `${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/references/measures.md` にある。作業を始める前に必ず読む。
- Tier 0 の基準は `${CLAUDE_PLUGIN_ROOT}/skills/workflow-tier0-rules/SKILL.md` にある。
- 実行時間・費用の計測には `${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh` を使う（使い方はスクリプト冒頭のコメント）。リポジトリのルートで実行する。

## Tier ごとの扱い

| Tier | 扱い | 施策 | 検証 |
|---|---|---|---|
| 0 | 必ず対応する | `timeout-minutes` / `concurrency` / 軽いジョブの `ubuntu-slim` | 不要 |
| 1 | 必ず対応する | 実行条件の見直し（対象ブランチ・paths） | 不要（動作の確認のみ） |
| 1 | 必ず対応する | キャッシュ | **要** |
| 2 | **ユーザーに確認せず** 検証し、効果があれば適用する | ARM ランナー / Vitest の `isolate: false` / テストの並列化 | **要** |
| 3 | **ユーザーが選んだもの** を対応する | Draft PR のスキップ / デフォルトブランチへの push もキャンセル対象にする | 不要（動作の確認のみ） |
| 3 | **ユーザーが選んだもの** を検証し、効果があれば適用する | CI 本体を `ubuntu-slim` に | **要** |

- Tier 2 は、効果を CI の計測で判断でき、代償（速さや技術的なリスク）を計測と PR のレビューで確認できる施策である。Tier 3 は、計測では良し悪しを決められず、開発体験や運用方針（Draft 中に CI の結果が見えない、待ち時間が延びる、未検証のコミットが残る）とのトレードオフになる施策である。
- **検証が不要な施策**は、実行回数を減らすなど、実行時間やランナーに依存しない改善である。計測せずに最終的な PR に含める。
- **検証が必要な施策**は、実行時間やランナーに依存する改善である。ワークフローごとに検証用 PR を作って計測し、効果があったものだけを最終的な PR に含める。

## 守ること

- **検証用 PR はマージしない。** 計測が終わったらクローズし、ブランチを削除する。採用した変更は最終的な PR に入れ直す（計測用の空コミットを最終的な PR に持ち込まないため）。
- **最終的な PR もマージしない。** マージはユーザーが行う。
- デプロイ・リリース・外部への書き込みを行うワークフローは、キャンセル対象にしない。ランナーを変える場合も、デプロイ先と同じアーキテクチャが必要かを必ず確認する。
- 推測で効果を報告しない。数値は計測した値だけを使い、計測できなかったものは「未計測」と書く。

## 手順

### 1. 前提の確認

1. リポジトリの情報を REST API で確認する（`gh repo view` は GraphQL を使うため、環境によっては動かない）。

   ```bash
   repo=$(git remote get-url origin | sed -E 's#^(https://[^/]+/|git@[^:]+:|ssh://git@[^/]+/)##; s#\.git$##')
   gh api "repos/$repo" --jq '{visibility, default_branch, push: .permissions.push}'
   ```

2. `visibility` が `public` の場合は、「パブリックリポジトリの標準ランナーは無料のため、対応不要」と報告して終了する。
3. `push` が `false` の場合や、`gh` が使えない場合は、何ができないかを伝えて終了する。

### 2. 現状の把握

1. `.github/workflows/` 配下のワークフローをすべて読む。各ジョブのトリガー・ランナー・処理内容・`timeout-minutes`・`concurrency` を把握する。
2. 直近 30 日の使用量を集計し、費用の大きいワークフロー・ジョブと、その実行回数を把握する。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" usage 30
   ```

3. 検証の対象になりそうなワークフローについて、デフォルトブランチでの直近の成功した実行を **3 回以上** 計測し、ベースラインとして記録する。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" baseline <workflow.yml> "" 5
   ```

   成功した実行が 3 回未満のワークフローは、報告で「ベースラインの信頼度が低い」と明記する。

### 3. 事前評価

`measures.md` を基に、施策ごとに当てはまるかを評価する。

- Tier 0・Tier 1：違反している箇所・当てはまる箇所を洗い出す。当てはまらないものは「該当なし」または「対応済み」とする。
- Tier 2：「自動で進める条件」を満たすかを評価する。満たさないものは「該当なし」または「要相談」とする。
- Tier 3：当てはまりそうか・主なリスクを評価する（質問の選択肢の説明に使う）。
- 各ワークフローの **外部への影響** を、定義から大まかに判断する。デプロイ・リリース、パッケージやイメージの公開、リポジトリへの push、PR・Issue へのコメントやラベル付け、外部サービスへの通知などを行うものは「外部への影響あり」とし、その根拠（コマンド、action、`permissions` の書き込み権限など）を控えておく。判断はあくまで目安で、漏れは手順 4 でユーザーに確認してもらう。

そのうえで、検証が必要な施策を **ワークフロー（ジョブ）ごと** にまとめ、手順 6 の順番に並べた検証計画を作る。

検証計画を作るときは、**検証用 PR で、変更後のワークフロー定義を安全に繰り返し実行できるか** をワークフローごとに確認する。

| ワークフローのトリガー | 検証用 PR での扱い |
|---|---|
| `pull_request`（`paths` なし、または `paths` が PR の変更ファイルに一致する） | そのまま検証できる。`pull_request` の `paths` は PR 全体の差分で判定されるため、空コミットでも再実行される |
| `pull_request`（`paths` が PR の変更ファイルに一致しない） | 検証用ブランチでだけ、`paths` に検証対象のワークフローファイル自身を一時的に追加する |
| `push`（`branches` がデフォルトブランチだけ、または `paths` がある）のみ | 検証用ブランチでだけ、`pull_request` トリガーを一時的に追加する。ただし下の「検証しないもの」に当たる場合は追加しない |
| `pull_request_target` | ベースブランチ側の定義で動くため、PR の変更を検証できない。副作用がない場合だけ、検証用ブランチで `pull_request` トリガーを一時的に追加する |
| `workflow_dispatch` がある | `gh workflow run <workflow.yml> --ref <検証用ブランチ>` で、検証用ブランチの定義を手動実行してもよい |

- **検証しないもの**：デプロイ・リリース・外部への書き込み（パッケージの公開、コメントやラベルの付与、外部サービスへの通知など）を行うワークフロー。検証のために実行すると副作用が起きるため、検証が必要な施策は「検証を見送った」として報告する。
- 一時的に追加したトリガーや `paths` は、最終的な PR に含めない。

### 4. ユーザーへの確認

まず、事前評価の結果を **ワークフローの一覧** として示す。

| ワークフロー | トリガー | 外部への影響（根拠） | 検証用 PR で起動するか | 扱い |
|---|---|---|---|---|
| 例：deploy | push（main） | あり（`sam deploy`） | しない | 検証しない |
| 例：ci | pull_request | あり（PR のブランチに `git push`） | する | 検証しない（ただし検証用 PR で起動する） |
| 例：test | pull_request | なし | する | 検証する（ランナー、キャッシュ） |

- 「扱い」には、検証する場合は検証する段階を、検証しない場合はその理由を書く。
- 外部への影響がありながら検証用 PR で起動するワークフローは、目立つように示す。

続けて、AskUserQuestion で次の 4 つを確認する。質問の前置きとして、Tier 0・Tier 1・Tier 2 は確認なしで対応することを伝える。

- 質問 1（Tier 3、複数選択）：Draft PR のスキップ / CI 本体を `ubuntu-slim` に / デフォルトブランチへの push もキャンセル対象にする。各選択肢の説明に事前評価の結果を書く。当てはまらない施策も選択肢に残し、「該当なし（理由）」と書く。
- 質問 2（検証）：「検証用 PR で CI を複数回実行して、効果のあるものだけ適用する（推奨）」/「検証が必要な施策は見送り、検証が不要な施策だけ対応する」。
- 質問 3（最終的な PR のまとめ方）：「すべての改善を 1 つの PR にまとめる」/「ワークフローごとに PR を分ける」。変更するワークフローが少ない（目安：3 つ以下）なら前者を、多いなら後者を推奨にする。ユーザーから指示があればそれに従う。
- 質問 4（対象の確認）：「この一覧のとおりで進める」/「外部への影響があるワークフローや対象を修正する」。修正が選ばれた場合は、指示に従って一覧を直し、もう一度示して確認する。外部への影響があるのに見落としていたワークフローは「検証しない」に変え、検証用 PR で起動する場合は、検証用ブランチでだけ一時的にトリガーを外すかをユーザーに確認する。

### 5. 検証の見積もりと確認

質問 2 で検証が選ばれた場合、Tier 3 の回答を反映した検証計画から、検証にかかる実行回数と費用を見積もって示す。

| 検証用 PR | 検証する段階 | push の回数 | 1 回の push で起動するワークフロー・ジョブ | 1 回の push あたりの費用（ベースライン） | 見積もり |
|---|---|---|---|---|---|
| 例：CI | ランナー（slim → ARM）、キャッシュ、並列化 | 3 回 × 4 段階 + キャッシュの初回 1 回 = 13 回 | CI / test、CI / lint、build / image | $0.030 | 約 $0.39 |

- push の回数は、段階ごとに N 回（既定は 3 回。キャッシュの段階はキャッシュが空の初回を加えて N + 1 回）とする。ランナーの段階で slim と ARM の両方を試す場合は 2 段階と数える。
- **1 回の push で起動するすべてのワークフロー・ジョブ** を費用に含める。検証用 PR への push では、検証対象以外のワークフロー（同じ PR の変更ファイルに `paths` が一致するもの、検証用ブランチへの `push` で動くものなど）も起動するため。ワークフローの定義と、検証用 PR の変更ファイルから、起動するものを洗い出す。
- 費用は「push の回数 × 1 回の push で起動するジョブのベースラインの費用の合計」で見積もる。ランナーを変えても、実行時間が延びれば費用は増えうるため、施策の段階のほうが安いとは仮定しない。
- 合計と、直近 30 日の使用量に対する割合も示す。

AskUserQuestion で「この見積もりで検証を進める（N = 3）」/「各段階の計測を 2 回に減らす（N = 2）」/「検証が必要な施策は見送る」を確認する。ここで決めた N を、手順 6 の計測回数に使う。

### 6. 検証用 PR で計測する

検証が必要な施策を、**ワークフロー（ジョブ）ごとに 1 つの検証用 PR** で計測する。

1. デフォルトブランチから検証用ブランチを作り、PR を作成する。タイトルは `[検証] <ワークフロー名> のコスト削減`、本文に検証計画を書く。Draft にはしない（Draft PR のスキップが設定済みだと CI が動かないため）。手順 3 で一時的なトリガーや `paths` の追加が必要としたワークフローは、最初のコミットでそれを追加する（このコミットは計測の段階に含めず、最終的な PR にも含めない）。
2. 次の順番で、段階ごとに変更をコミットして計測する。前の段階で採用した変更の上に、次の段階を積み上げる。
   1. **ランナー**：slim と ARM は同じジョブで両立しないため、1 つの段階として扱う。
      - Tier 3 で slim が選ばれ、ジョブが slim の条件を満たす場合は、まず slim を試す。
      - slim を採用しなかった場合（または試さなかった場合）は、そのコミットを `git revert` し、ARM が Tier 2 の条件を満たせば ARM を試す。
   2. **キャッシュ**（Tier 1）
   3. **Vitest の `isolate: false`**（Tier 2）
   4. **テストの並列化**（Tier 2）：並列数の効果はランナーのコア数に左右されるため、ランナーを決めた後に、そのランナーで試す。並列数は「コア数」と「コア数の 2 倍」を比べる（slim は 1 vCPU のため、テストが待ち時間を多く含む場合だけ試す）。
3. 各段階の計測：
   - 変更をコミットして push し、CI が完了したら、空コミット（例：`ci: 効果計測のための空コミット（2/N）`）を push して再実行する。これを、手順 5 で決めた N 回の実行がそろうまで繰り返す（キャッシュの段階は、キャッシュが空の初回を除いて N 回）。N 回を超えて実行しない。`workflow_dispatch` で検証するワークフローは、空コミットの代わりに `gh workflow run` で N 回実行する。
   - concurrency の設定で実行中の CI がキャンセルされるため、**前の実行が完了してから** 次の空コミットを push する。
   - 各実行を計測する。

     ```bash
     bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" sha <commit-sha> <workflow.yml>
     ```

4. 各段階の判定：**すべて満たした場合だけ「採用」**とする。満たさない場合は、その段階のコミットを `git revert` してから次の段階に進む。
   - すべての実行が成功している。
   - 対象ジョブの **1 回あたりの平均費用**（平均課金分数 × 単価）が、**直前に採用した状態**（最初はベースライン）より下がっている。
   - `ubuntu-slim` の場合、どの実行も 15 分の上限まで十分余裕がある（目安：10 分未満）。
5. 失敗した場合は、原因が施策によるものかを調べる。`measures.md` の「よくある失敗と対処」で直せるなら直して、その段階を計測し直す（計測し直すのは 2 回まで）。直せない場合は「不採用」とする。Tier 2 で、自動で進める条件を超える変更が必要だと分かった場合も、そこでやめて「要相談」とする。
6. すべての段階が終わったら、段階ごとの計測結果（各回の時間・課金分数・平均費用と、直前の状態との比較）と採否を PR にコメントし、**検証用 PR をクローズしてブランチを削除する**。

### 7. 最終的な PR を作る

手順 4 の質問 3 で選ばれたまとめ方で、デフォルトブランチから最終的な PR を作る。

- 含めるもの
  - 検証が不要な施策：Tier 0、Tier 1 の実行条件の見直し、ユーザーが選んだ Tier 3（Draft PR のスキップ、デフォルトブランチへの push のキャンセル）
  - 検証用 PR で「採用」になった変更（計測用の空コミットは含めない）
- 本文には、施策ごとに変更内容・計測結果（ベースライン → 施策後の 1 回あたりの平均費用）・検証用 PR へのリンクを書く。
- 最終的な PR の CI が成功することを確認する（繰り返しの計測はしない）。
- 動作を確認する施策は、意図どおりに動くかを確認する。
  - 実行条件の見直し：対象外の変更でワークフローが起動しないこと、対象の変更で起動することを、ワークフローの定義と PR の CI から確認する。
  - Draft PR のスキップ：Draft の状態ではジョブがスキップされ、Ready for review にすると実行される設定になっていることを確認する。
  - push のキャンセル：デプロイ系のワークフローが対象外であることを確認する。
- ワークフローごとに PR を分けた場合、同じファイルを変更する PR がないかを確認し、あれば報告する。

### 8. 報告

最後に、次の形式で報告する。

1. **対応したもの**（施策 / 最終的な PR / 変更内容 / ベースライン → 施策後の 1 回あたりの平均費用 / 月額の削減見込み）
   - 月額の削減見込み = (ベースラインの 1 回あたりの費用 − 施策後の 1 回あたりの費用) × 直近 30 日の実行回数
   - 検証が不要な施策は「未計測（実行回数の削減）」と書き、マージ後に確認する方法を添える。
2. **対応しなかったもの**（施策 / 理由）。理由は次のいずれかで書く。
   - 該当なし（例：Vitest を使っていない）
   - 対応済み（すでに満たしていた）
   - 要相談（Tier 2 で、自動で進める条件を超える変更が必要だった。必要な作業の内容を書く）
   - ユーザーが選択しなかった（Tier 3）
   - 検証で効果がなかった・失敗した（計測値と検証用 PR へのリンクとともに）
   - 検証を見送った（手順 4・5 で選ばれた場合）
3. **検証にかかった実行回数と費用**（手順 5 の見積もりとの比較。検証用 PR で起動したすべてのワークフローを含める。`measure.sh sha <commit-sha>` をワークフロー名なしで実行すると、そのコミットで起動した全ワークフローの合計が出る）
4. **注意点**（PR 同士の競合、ユーザーが手作業で行う必要があること など）
