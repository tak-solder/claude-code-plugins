# GitHub Actions の実行コスト削減

現在のリポジトリの GitHub Actions ワークフローを見直し、実行コストを下げる。

- 施策の詳細（効果・リスク・判断基準・料金）は `${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/references/measures.md` にある。作業を始める前に必ず読む。
- Tier 0 の基準は `${CLAUDE_PLUGIN_ROOT}/skills/workflow-tier0-rules/SKILL.md` にある。
- 実行時間・費用の計測には `${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh` を使う（使い方はスクリプト冒頭のコメント）。リポジトリのルートで実行する。

## 守ること

- **1 施策 1 PR** にする。効果を施策ごとに測れるようにするため。各 PR はデフォルトブランチから作る。
- **PR をマージしない。** マージはユーザーが行う。
- デプロイ・リリース・外部への書き込みを行うワークフローは、キャンセル対象にしない。ランナーを変える場合も、デプロイ先と同じアーキテクチャが必要かを必ず確認する。
- 推測で効果を報告しない。数値は計測した値だけを使い、計測できなかったものは「未計測」と書く。
- 同じファイルを変更する PR が複数できる場合は、マージ後に競合が起きうることを報告に書く。

## Tier ごとの扱い

| Tier | 扱い | 施策 |
|---|---|---|
| 0 | 必ず対応する | `timeout-minutes` / `concurrency` / 軽いジョブの `ubuntu-slim` |
| 1 | 必ず対応する | 実行条件の見直し（対象ブランチ・paths） / キャッシュ |
| 2 | **ユーザーに確認せず** 検証し、効果があれば適用する | ARM ランナー / Vitest の `isolate: false` / テストの並列化 |
| 3 | **ユーザーが選んだもの** を検証し、効果があれば適用する | Draft PR のスキップ / CI 本体を `ubuntu-slim` に / デフォルトブランチへの push もキャンセル対象にする |

Tier 2 は、効果を CI の計測で判断でき、代償（速さや技術的なリスク）を計測と PR のレビューで確認できる施策である。Tier 3 は、計測では良し悪しを決められず、開発体験や運用方針（Draft 中に CI の結果が見えない、待ち時間が延びる、未検証のコミットが残る）とのトレードオフになる施策である。

## 手順

### 1. 前提の確認

1. リポジトリの情報を REST API で確認する（`gh repo view` は GraphQL を使うため、環境によっては動かない）。

   ```bash
   repo=$(git remote get-url origin | sed -E 's#^(https://[^/]+/|git@[^:]+:|ssh://git@[^/]+/)##; s#\.git$##')
   gh api "repos/$repo" --jq '{visibility, default_branch, push: .permissions.push}'
   ```

2. `visibility` が `public` の場合は、「パブリックリポジトリの標準ランナーは無料のため、対応不要」と報告して終了する。
3. `push` が `false` の場合や、`gh` が使えない場合は、何ができないかを伝えて終了する。

### 2. 現状の把握

1. `.github/workflows/` 配下のワークフローをすべて読む。各ジョブのトリガー・ランナー・処理内容・`timeout-minutes`・`concurrency` を把握する。
2. 直近 30 日の使用量を集計し、費用の大きいワークフロー・ジョブを特定する。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" usage 30
   ```

3. 費用の大きいワークフローから順に、デフォルトブランチでの直近の成功した実行を **3 回以上** 計測し、ベースラインとして記録する。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" baseline <workflow.yml> "" 5
   ```

   成功した実行が 3 回未満のワークフローは、報告で「ベースラインの信頼度が低い」と明記する。

### 3. 事前評価と、Tier 3・検証方法の確認

1. `measures.md` の「自動で進める条件」を基に、Tier 2 の各施策がこのリポジトリに当てはまるかを評価する。条件を満たさない施策は実装せず、「該当なし（理由）」または「要相談（理由）」として報告に回す。
2. Tier 3 の各施策についても、当てはまりそうか・主なリスクを評価する。
3. AskUserQuestion で次の 2 つを確認する。
   - 質問 1（Tier 3、複数選択）：Draft PR のスキップ / CI 本体を `ubuntu-slim` に / デフォルトブランチへの push もキャンセル対象にする。各選択肢の説明に事前評価の結果を書く。当てはまらない施策も選択肢に残し、「該当なし（理由）」と書く。
   - 質問 2（検証方法）：「PR を作成し、検証のために空コミットを push して CI を複数回実行する（推奨）」/「ブランチと PR の作成までにとどめ、検証はユーザーが行う」。
4. 質問の前置きとして、**Tier 2 の施策（事前評価で当てはまったもの）は確認なしで実装・検証すること**と、**検証のために施策ごとに CI を 3 回以上実行し、その分の実行時間が課金されること**を伝える。

どれも選ばれなかった場合、Tier 3 は対応しない。

### 4. Tier 0・Tier 1 を対応する（必須）

Tier 0 と Tier 1 は、ユーザーの選択に関係なく必ず対応する。施策ごとに PR を分ける。

- **Tier 0**：`workflow-tier0-rules` の 3 つのルール（`timeout-minutes`、`concurrency`、軽いジョブの `ubuntu-slim`）に違反している箇所を直す。すでに満たしている場合は「対応済み」として報告する。
- **Tier 1-1 実行条件の見直し**：関係のないブランチやファイルの変更で動いている重いワークフローがあれば、`branches` / `paths` を絞る。`paths` を足す前に、branch protection の required checks を確認する（`measures.md` 参照）。
- **Tier 1-2 キャッシュ**：毎回同じ依存のインストールやビルドをしている箇所にキャッシュを入れる。

当てはまる箇所がない施策は、PR を作らず「該当なし（理由）」として報告する。

### 5. Tier 2 と、選択された Tier 3 を実装する

Tier 2（事前評価で当てはまったもの）と、ユーザーが選んだ Tier 3 の施策ごとに、デフォルトブランチから新しいブランチを作って実装し、PR を作る。PR の本文には、背景・変更内容・ベースラインの数値・確認してほしいことを書く。

Tier 2 の実装中に、事前評価の条件を超える変更が必要だと分かった場合（例：並列化のために DB をワーカーごとに分ける仕組みが要る）は、そこで実装をやめ、PR をクローズして「要相談」として報告する。

### 6. 複数回検証し、効果があるものだけを適用する

手順 3 で「検証は PR の作成まで」が選ばれた場合は、Tier 2 も含めてこの手順を飛ばし、報告で「未検証」と書く。

#### 実行時間・費用を比べる施策（Tier 1-2 キャッシュ、Tier 2 のすべて、Tier 3 の `ubuntu-slim`）

1. PR の CI を **3 回以上** 実行する。最初の実行のあと、空コミットを push して再実行する。
   - concurrency の設定で実行中の CI がキャンセルされるため、**前の実行が完了してから** 次の空コミットを push する。
   - 空コミットのメッセージには、計測用であることを書く（例：`ci: 効果計測のための空コミット（2/3）`）。
   - キャッシュの施策は、キャッシュが空の初回を除いて 3 回計測する（合計 4 回以上）。
2. 各実行を計測する。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/private-actions-cost-reduction/scripts/measure.sh" sha <commit-sha> <workflow.yml>
   ```

3. 判定する。**すべて満たした場合だけ「適用」**とする。
   - すべての実行が成功している。
   - 対象ジョブの **1 回あたりの平均費用**（平均課金分数 × 単価）が、ベースラインより下がっている。
   - `ubuntu-slim` の場合、どの実行も 15 分の上限まで十分余裕がある（目安：10 分未満）。
4. 失敗した場合は、原因が施策によるものかを調べる。`measures.md` の「よくある失敗と対処」で直せるなら直して再検証する（再検証は 2 回まで）。直せない場合は「不採用」とする。

#### 動作を確認する施策（Tier 1-1、Draft PR のスキップ、デフォルトブランチへの push のキャンセル）

実行時間ではなく、意図どおりに動くかを確認する。

- 実行条件の見直し：対象外の変更でワークフローが起動しないこと、対象の変更で起動することを、PR の CI とワークフローの定義から確認する。
- Draft PR のスキップ：Draft の状態ではジョブがスキップされ、Ready for review にすると実行されることを確認する。
- push のキャンセル：デプロイ系のワークフローが対象外であることを確認する。

#### 判定後の扱い

- **適用**：PR を開いたままにし、計測結果（各回の時間・課金分数・平均費用とベースラインの比較）を PR にコメントする。空コミットは、マージ時に squash すれば履歴に残らないことも書く。
- **不採用**：計測結果と不採用の理由を PR にコメントしてから、PR をクローズし、ブランチを削除する。

### 7. 報告

最後に、次の形式で報告する。

1. **対応したもの**（施策 / PR / 変更内容 / ベースライン → 施策後の 1 回あたりの平均費用 / 月額の削減見込み）
   - 月額の削減見込み = (ベースラインの 1 回あたりの費用 − 施策後の 1 回あたりの費用) × 直近 30 日の実行回数
2. **対応しなかったもの**（施策 / 理由）。理由は次のいずれかで書く。
   - 該当なし（例：Vitest を使っていない）
   - 要相談（Tier 2 で、自動で進める条件を超える変更が必要だった。必要な作業の内容を書く）
   - ユーザーが選択しなかった（Tier 3）
   - 検証で効果がなかった・失敗した（計測値とともに）
   - 対応済み（すでに満たしていた）
3. **未計測・未検証のもの**と、その確認方法
4. **注意点**（同じファイルを変更する PR の競合、ユーザーが手作業で行う必要があること など）
